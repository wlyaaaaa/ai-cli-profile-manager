## 2. 产品定义

一句话：让 Windows 用户用一个中文入口，按经过验证的 Profile 启动原生 Codex CLI、Claude Code 或当前官方 Rust Open Interpreter，不再反复手改全局环境变量、配置文件和代理进程。

本产品是启动与运维层，不是新的 AI Agent。聊天、历史、终端交互、权限提示、上下文管理和工具执行继续由原生 CLI 负责。

2026-09-15：既有 `codex-qwen3-8-max-paygo` 保留稳定 Profile ID、北京 Workspace 按量端点与凭据绑定，模型身份从可变 alias 固定为 `qwen3.8-max-0902`。Codex Desktop 桥接继续在每次引擎启动时读取原生官方目录，再合并已配置的 0902 与本地模型；云端 Provider 使用 Codex 官方 command-backed auth 通道按需取得 AICLI 加密副本，不把密钥写进模型目录、基础配置或全局环境变量。Password Center 的 `qwen-default` 是上游凭据管理入口，AICLI Codex Profile 是所需运行副本。

2026-09-16：新增 `codex-glm-5-3` 与 `codex-glm-5-3-flash` 两个 exact 中国区 Responses Profile，精确模型 ID 分别为 `glm-5.3` 与 `glm-5.3-flash`，端点固定 `https://open.bigmodel.cn/api/v1`。两者使用独立 Provider/单模型目录、1M 上下文、最大上下文 90% 自动压缩阈值和 `low/high/max`，不加入 Ollama 本地模型集合。Codex Desktop 继续从原生在线缓存取得 OpenAI 模型后合并这两项；Password Center 的 `zhipu-glm-api` 是规范凭据来源，两个 AICLI Profile 是所需加密运行副本。

目标用户：

1. 已使用 Codex CLI、Claude Code 或 Open Interpreter，但需要切换官方订阅、国内 API 和本地模型的 Windows 用户。
2. 会使用 PowerShell，但不希望记忆 Provider、URL、套餐、模型和代理细节的用户。
3. 需要同一套可靠配置跨项目使用，同时不污染官方登录状态的用户。

核心原则：

- 原生优先：不重做 TUI、PTY、会话历史或协议网关。
- 明确选择：用户知道本次引擎、Provider、模型、凭据来源和数据去向。
- 进程隔离：不永久写全局 Provider 变量，不覆盖用户基础配置。
- 证据优先：能打开 CLI 不等于模型或工具可用。
- 安全失败：端口、身份、摘要、秘密和配置冲突不确定时拒绝危险动作。
- 可退出：`native` 和 `eject` 让用户能理解、迁移和脱离本工具。

## 4. 产品对象与数据模型

### 4.1 三层对象

1. **Provider 模板**：随版本发布的只读声明，记录引擎、Provider、套餐、地域、transport、端点、模型、认证类型、能力、来源和兼容性。
2. **用户 Profile**：保存模板 ID、用户自定义 ID/名称、地域、模型、项目偏好和秘密引用，不保存秘密值。
3. **启动计划**：每次 `start` 临时生成，包含可执行文件、工作目录、参数、子进程环境、移除变量、配置文件和代理依赖。

### 4.2 Manifest 基本字段

`schemaVersion`、`id`、`displayName`、`engine`、`provider`、`plan`、`region`、`transport`、`endpoint`、`models`、`auth`、`proxyRef`、`capabilities`、`compatibility`、`verification`、`sources`、`deprecation`。

Manifest 是无执行能力的数据，不允许嵌入 PowerShell。URL、Header、模型和 ID 在进入启动计划前验证；非 localhost 明文 HTTP 默认拒绝。

### 4.3 状态闭集

- `通过`：单个检查项成功。
- `可用`：当前版本要求的真实验证均有证据。
- `可用但有限制`：静态就绪、文本通过但工具未证明，或存在明确限制。
- `不可用`：关键依赖、协议、配置或真实测试失败。

验证记录必须绑定 Profile 指纹、引擎、Provider、transport、端点、模型、CLI 路径/版本、测试层和时间。配置或版本变化后旧证据不能无条件继承。

```text

aicli proxy <ccp|cliproxy> install
aicli proxy ccp login [codex|device]
aicli proxy cliproxy login [codex|claude|device]
aicli proxy <ccp|cliproxy> logout [--purge-local-auth] [--yes]
aicli proxy <ccp|cliproxy> configure [--port <port>|--auto-port]
aicli proxy <ccp|cliproxy> start|stop|status [--json]
aicli proxy <ccp|cliproxy> update-check|update|native

aicli update check [codex|claude|ollama|interpreter|ccp|cliproxy|self] [--json]
aicli update guide [codex|claude|ollama|interpreter|ccp|cliproxy|self]

aicli help [compact|model|effort|permissions|resume|compare|<command>]
aicli uninstall [--purge-user-data] [--yes]
```

规则：

- 无参数入口是短文本选择器，不是全屏界面。
- 未给 `--project` 时使用当前目录，目录必须存在。
- 只有 `--` 后的字符串逐项传给上游。
- 与启动计划冲突的 Provider、Base URL、认证和产品自管配置入口必须拒绝。
- 未知命令、参数和值缺失立即返回用法错误，不猜用户意图。
- 删除型动作默认确认；`--yes` 只授权该命令列出的本地删除。
- `test` 必须显式 `--live`；非交互需 `--yes`。

退出码：`0` 成功、`2` 用法错误、`3` 可用但有限制、`4` 不可用、`5` 内部错误、`6` 取消。

## 6. 文件、秘密与进程合同

### 6.1 默认布局

| 内容 | 位置 |
|------|------|
| 用户 Profile/设置 | `%APPDATA%\AiCliProfileManager` |
| 秘密、代理、状态、缓存、日志 | `%LOCALAPPDATA%\AiCliProfileManager` |
| CurrentUser PowerShell 模块 | 当前用户 `PSModulePath` 下的版本目录 |
| 命令垫片 | `%LOCALAPPDATA%\aicli\bin` |

所有路径通过 Windows Known Folders 或实际 `PSModulePath` 解析，不在公开模板中硬编码用户目录或盘符。

### 6.2 秘密

- API Key 使用 DPAPI CurrentUser；安全存储失败时不得回退明文。
- 秘密不得出现在 Git、命令参数、PowerShell 历史、日志、JSON、异常、`show`、`native`、`eject` 或测试快照。
- 代理 OAuth 由上游代理写入隔离目录，产品不读取 token 正文。
- 删除最后一个秘密引用的用户 Profile 时，可同时删除本工具保存的密文，但必须在动作前说明。

### 6.3 子进程

- 使用 `ProcessStartInfo.ArgumentList`，不拼接字符串执行，不对用户输入 `Invoke-Expression`。
- Provider 环境只进入目标子进程；父终端保持不变。
- machine child 先清空继承环境，再从 Windows、PowerShell、Node/TLS 所需的小型 allowlist 重建；父环境中的无关凭据、Provider 配置和调试变量不得默认进入子进程。受管计划最后通过 `EnvironmentDelta` 显式注入本次 Profile 必需的 Provider/运行时变量；该显式增量是受信任权限边界。
- `native` 必须展示脱敏后的实际计划；`eject` 只生成无秘密配方。

## 7. 引擎适配合同

### 7.1 Codex

- 公开第三方 transport 只接受 Responses。
- 交互式官方 Profile 使用真实 `CODEX_HOME` 与官方登录；machine run 只复制现有 `auth.json` 到独占 `CODEX_HOME`，不复制配置、规则、技能或其他会话，也不要求付费 API Key。可恢复 run 在终态前持久保留该 home 以支持真实 `thread/resume`；一次性 capture/Live 仍在结束时清理。
- 第三方 Profile 在真实 Codex home 下只写 `aicli-` 命名空间的独立 Profile 文件，并记录受管标记和内容 hash。
- 不覆盖基础 `config.toml` 或未知文件；用户修改后的受管文件不误删。
- 当前 Codex Profile 格式为 `$CODEX_HOME/<name>.config.toml`；旧 `[profiles.*]` 语法不作为当前合同。
- DeepSeek Flash 0731 与 Pro 0813 的官方模型身份分别进入隔离目录，并以内容寻址文件发布到 `aicli-model-catalogs` 受管命名空间；Profile 与 machine override 统一引用同一绝对 `model_catalog_json`。目录只含对应 exact alias，模型版本、Responses 与 max effort 纳入 Profile 指纹。
- Qwen3.8 Max 0902 使用独立 `qwen3.8-max-0902-codex.json`；Qwen3.7 06-08 使用独立 `qwen3.7-max-2026-06-08-codex.json`。两者固定 983616/95%、compact 885254（最大上下文 90%）和用户 `max` → 原生 `xhigh`。Qwen3.8 可变 alias/preview 与其他 Qwen3.7 Max/Plus 的模型、兼容入口和生成分支仍为 tombstone；本地 Qwen 使用各自独立 262144 目录并在 235929（90%）自动压缩。生成器除提示载荷外必须白名单声明能力，禁止照抄空 `base_instructions` 或静默继承其他 Provider 能力后宣称 Agent 行为不变。

## 8. ChatGPT 双代理与端口合同

固定上游：

- `ccp`：`raine/claude-code-proxy`，首选端口 `43197`。
- `cliproxy`：`router-for-me/CLIProxyAPI`，首选端口 `43198`。

### 8.1 供应链

- 任一 Windows artifact 必须匹配产品随版本发布的精确 SHA256，或固定可信发布者签名。
- HTTPS、GitHub 来源、下载后临时算摘要或“上游没有 checksum”不能替代批准证据。
- 解压前枚举条目并拒绝绝对路径、`..`、链接逃逸和清单外可执行文件。
- 首次安装在临时目录完成摘要、安全解压和结构验证后才设置 `current`；启动时完成进程身份、健康响应与 loopback 监听验证后才保存运行状态。`0.1.0` 不执行已安装代理的受管版本切换；后续版本若启用更新，必须先完成运行健康验证并支持失败回滚。

### 8.2 端口

- 只允许 IPv4 loopback `127.0.0.1`；`0.0.0.0`、`::`、局域网和公网监听均失败并停止本次受管进程。
- 候选池为 `43192-43209`，两个代理采用不同轮转起点。
- 分配时持有同用户互斥锁，排除 TCP 动态范围、Windows excluded ranges、活动 listener 和真实 bind 失败。
- 不修改动态端口范围、excluded range、防火墙或 URL ACL，不杀未知占用进程。
- 成功启动并验证新进程持有 listener 后才持久化端口。

### 8.3 身份和生命周期

运行状态记录代理 ID、PID、启动时间、可执行路径、版本目录、配置路径、host、port 和 nonce。停止、更新或卸载前重新核验 PID、启动时间、路径和 listener；身份不匹配不终止。

登录只调用上游交互，不读取 OAuth 正文。`logout` 必须分别报告本地清理和远程撤销；强制删除本地认证目录不等于远程撤销。

## 9. Doctor 与 Live Test 合同

### 9.1 Doctor

按稳定 check ID 检查：平台与 PowerShell、CLI/代理/Ollama 版本、安装来源、登录状态、Manifest/Profile/schema/秘密引用、父环境与有效配置层冲突、套餐/地域/端点/模型、代理身份和 listener、Ollama 服务/模型、验证记录有效性。

### 9.2 Live Test

1. 必须显式 `--live`，先展示 Provider、数据去向和额度风险。
2. 创建随机临时空目录，不读取用户项目。
3. 使用真实目标 CLI 的非交互入口。Codex 保持通用 `danger-full-access` 合同，并且只有最终观测到零次工具调用才通过；首个工具事件触发终止，但不是执行前工具禁用。其他引擎隔离私人规则、设置、MCP、Hooks、Skills 和普通工具。
4. 文本层要求进程退出码 0 且最终模型正文严格等于 `PONG`。
5. 工具层只暴露不接受任意路径/命令的 nonce 工具；无法隔离时跳过并报告限制。
6. 保存结构化版本和 Profile 指纹，不保存提示、回复、项目文件或秘密。
7. `finally` 清理临时配置、工具进程和目录；异常也要覆盖旧验证记录。

### D-028：Open Interpreter 世代切换

首版只支持当前官方 Rust Open Interpreter `0.0.21+`，拒绝旧 Python 0.4.x。Provider 采用 Rust CLI 的 TOML 配置与环境密钥引用，不能把旧参数兼容层继续作为公开能力。

### D-029：DeepSeek Codex Flash/Pro exact 接入

`0.3.4` 将 Codex 的 `deepseek-v4-flash` / `DeepSeek-V4-Flash-0731` 与 `deepseek-v4-pro` / `DeepSeek-V4-Pro-0813` 分成两个 Responses exact Profile，均固定 1M 与用户默认 `max`。Claude Code 走 Anthropic、Rust OI 走 Chat，并继续保持 Flash-only。Qwen Code 0.21 与 OpenCode 1.18.8 即使有上游原生支持，也不能绕过 AICLI 当前禁网 machine 沙箱：在真实 Key 可能进入 Shell 且缺少受控远程 egress relay 时，不创建假 Profile。

### D-030：第三方上下文连续性以原生 ChatGPT + Codex 为基准

原生 `codex-official` 不附加目录或压缩策略。第三方 Codex 无 OpenAI remote compact 时使用受管模型目录修正真实窗口，云千问与本地 Qwen 分离；Claude Code 只为已知模型设置官方支持的窗口变量，不设置提前压缩百分比，也不禁用溢出保护，未知模型会清除继承控制项；OpenCode 的一次性配置对 `qwen-main-v1` 显式声明 262144/8192，对固定 Qwen3.8-27B 256K 运行标签声明 262144/32768，并共用 20000 reserve、4 轮/16384 token 保留与 `prune=false`。这些设置只能延后并减少不必要的有损摘要，不能把摘要宣称为无损。

AI 使用合同：一个会话/run 对应一个内聚里程碑；AICLI 的 `aicli.third-party-continuity.v1` 契约要求主动 compact 前先把目标与验收、约束/授权/owner、规则与关键文件、改动及脏改动归属、决定、测试/Live 缺口、阻塞与下一步持久化到项目已有状态，压缩后把摘要当线索，重读项目规则、状态文档与工作树（`git status`/`git diff`），不建立第二事实源。难题与最终判断不得为节省 token 下放给能力未通过的模型。远程 Qwen/DeepSeek OpenCode 仍受 key-isolated egress relay 门禁，与压缩修复相互独立。

### D-031：PDF 构建必须有界并可视觉复核

两本 canonical Markdown 的 PDF 构建优先使用仓库随附 helper 调用本机已有 Playwright 与 Edge，隔离于日常浏览器进程；缺少该运行时时才进入有界超时的 Edge CLI 后备。生成物必须记录源 Markdown SHA256，完成文本抽取、全页渲染和代表性密集页检查后才能随文档提交，不能把“进程退出码为零”单独视作版面通过。

### D-032：Qwen3.7 Max/Plus 永久退役

Qwen3.7 Max/Plus 全家族不再是候选或兼容层：移除 Codex、Claude Code、Open Interpreter Manifest、目录、生成器分支和 OpenClaw 导入入口；旧用户 Profile、最终启动计划以及 native model/fallback 参数都必须命中统一 tombstone 并失败关闭。退役身份不能自动映射到 Qwen3.8，也不能通过旧安装 payload 或遗留受管 Codex 文件继续启动。

升级安装必须先作全量预检，再把身份闭合的退役入口移入可恢复 quarantine；任何未知或用户改写项阻断本次安装且不被删除。用户 SecretRef 保留，后续只能在身份相同的凭据域内显式复用，不进行明文迁移。

### D-033：所有 Codex harness 当前及未来模型一律完全访问

`aicli run` 的 Codex 路由按引擎而不是模型列表固定原生 `danger-full-access` 与 `approvalPolicy=never`。每个新模型、Provider 或本地 Profile 自动继承同一权限合同；请求较低权限不是兼容模式，而是调用前错误。桥接器必须从 app-server 回读 `dangerFullAccess`，同时回读 exact model/modelProvider 并拒绝 reroute。交互式 `aicli start` 仍由用户和原生 CLI 管理权限，不与 harness 合同混淆。

Codex 文本 Live 也必须走该通用 harness，并保存 exact runtime executable/version 与 `approval_policy`、`requested_policy`、`sandbox_boundary`、`sandbox_type`、`permission_profile` 五项运行时证据。本次 Live 额外要求观测到零次工具调用；首个工具事件触发终止和失败，但该机制不是执行前禁用、沙箱或降权。

### D-034：窄恢复 Qwen3.7 Max 06-08 exact Codex Profile

用户 2026-08-14 的新明确指令窄范围取代 D-032 的“全家族永久退役”：只新增 `codex-qwen3-7-max-paygo` → `qwen3.7-max-2026-06-08`。该入口固定北京 Workspace paygo Responses、单候选、无 fallback、983616/95%、compact 885254（最大上下文 90%），并把用户 `max` 映射原生 `xhigh`。同一 Workspace endpoint 才可显式复用 Qwen3.8 的不透明 SecretRef。

D-032 对通用 `qwen3.7-max`、05-20、preview、Plus、旧 Profile ID、Claude/OI/OpenClaw route、native model/fallback 和旧安装入口继续有效。06-08 仍在全局 tombstone matcher 中，以阻止自由模型覆盖；只有同时命中新 exact template/profile identity 的上下文门才允许。迁移同样必须按身份保留新 exact artifacts，而不是把“出现 06-08 字符串”直接当作旧入口。

### D-035：exact Codex Profile 使用快速启用与正式发布双车道

维护者从 clean commit 本机启用一个 exact Codex Profile 时，使用 `Install-ExactCodexProfileFast.ps1`。快速车道必须闭合 Manifest/目录单模型身份、Responses、`flexible=false`、用户 `max`、无 reserved/fallback、退役上下文门、one-command、SecretRef 与安全回归，再执行发行 smoke、原子安装和固定 shim 的 `list/show` 回读；它不得构建 PDF/ZIP、执行付费 Live 或把 `liveAcceptance=not-run` 冒充当前 Live。

正式公开发布仍需全量 Pester、canonical 文档/PDF、发行 ZIP/hash、公开暴露检查、Git 收口以及按授权执行的独立 Live。两条车道共享同一 source of truth；快速车道缩短本机可用等待时间，不降低 exact/no-fallback/secret/launch-plan 门禁。`--reuse-secret-from` 命中同一 Qwen Workspace 凭据域时同时盲复用规范化 endpoint，避免重复输入或回显 Workspace 标识。

### D-036：Google AI Pro / Antigravity 订阅通道只作为 Gemini 推理后端，Codex 仍是唯一 Harness

用户于 2026-09-17 明确选择“Google AI Pro → Antigravity → Gemini 3.8 Flash High → Codex Harness”，目标不是把 Codex Desktop 当 Antigravity 的外壳，而是让 Gemini 只承担模型推理，文件、Shell、MCP、动态工具、权限、项目规则、上下文与 thread 生命周期仍由原生 Codex Harness 负责。该路线不使用 Gemini API Key、Vertex API Key/ADC 或逆向 Google OAuth；认证只由官方 Antigravity consumer 客户端维护，AICLI 不读取、复制或持久化 OAuth token。

这不是把 Google Chat/Agent 端点伪装成上游原生 Responses。新增入口使用 `transport=managed-proxy`：AICLI 在本机 loopback 上实现真实的 Codex Responses 语义，再把一次模型决策翻译给官方 Antigravity consumer 通道。只有这一个明确登记、真实 Windows 验收的受管本地适配器可以作为“非上游原生 Responses”的窄例外；其他远端 Provider 继续受“上游明确支持 Responses、不得把 Chat Completions 冒充 Responses”的现行硬边界约束。

首个 exact 入口固定为 `codex-gemini-3-8-flash-antigravity` → `gemini-3.8-flash-high`，用户可见名称为 `Gemini 3.8 Flash`，Provider 显示为 `Google Antigravity`。禁止 alias、自动模型选择和 fallback；模型目录只声明 Antigravity 实际存在的 `low/medium/high`，默认 `high`，不得把 Codex `max/xhigh` 虚构为 Google 不存在的档位。上下文窗口、图片能力和压缩阈值没有当期证据前一律不猜。

生产优先使用 `agy` 的 custom-agent + `stream-json` consumer 通道：专用 Agent 必须 `tools: []`、`subagent: false`、`commandExecutionPolicy: off`、`excludeDefaultComponents: true`，并在隔离空 workspace 再挂全工具 `PreToolUse deny` 作为第二道机械保险。启动后的 `init.tools` 是运行时门禁；任何文件、Shell、Browser、Web、MCP、subagent、task 管理等真实 Antigravity 工具仍被暴露时，当前构建不得标记为可用。AICLI 只把 Codex 当前 request 声明的工具描述作为“虚拟工具意图”交给 Gemini，真正执行必须回到 Codex。

公开 Antigravity Python SDK 是优化候选，不是当前生产基线。只有在不设置 Gemini/Vertex API Key、也不依赖 Vertex ADC 的条件下，真实证明它能复用现有 Google AI Pro consumer 登录权益，才允许以 `CapabilitiesConfig(enabled_tools=[], enable_subagents=false)` 替换 CLI backend；否则立即判为不适用，不因 SDK 接口更干净而改变“复用 Pro 订阅”的目标。

Gemini 的可见思考采用“两级证据”合同：若官方 backend 暴露公开 thought/reasoning 文本，则映射到现有 Codex reasoning summary 展示；若只暴露 thinking token 计数，则绝不伪造隐藏思维，改由 Gemini 在结构化结果中显式生成面向用户的 `visible_summary`，作为公开进度/理由摘要。统一复用 `CodexUserCommunicationPolicy.ps1` 的中文、主动进度、重要发现和最终答复引导。DeepSeek 的 keep-alive 状态机不预先复制；只有当前 Codex Desktop renderer replay 对 Gemini 真实事件证明存在同一种尾部闪烁时才增加 provider-specific 修正。

在 custom-agent 零工具、Responses 工具闭环、取消/超时、consumer OAuth、模型 exact 身份、reasoning 展示、历史读取、Desktop 真选型和真实 Codex tool E2E 全部通过前，该 Profile 只能标为“设计/实验”，不得显示为正式可用。

## 22. Gemini 3.8 Flash High via Antigravity + Codex Harness 施工设计

### 22.1 用户结果与非目标

最终用户体验必须是：在 Codex Desktop 模型列表选择 `Gemini 3.8 Flash` 后，新建的真实 Codex thread 使用 `gemini-3.8-flash-high` 推理；Codex 继续拥有 Agent loop、Shell、文件读写、patch、MCP、动态 `public_web_search`、子代理、项目规则、审批/沙箱身份、上下文压缩、thread/history 与恢复。Antigravity 只承担 Google AI Pro consumer 认证和 Gemini 推理传输。

因此目标架构是：

```text
Codex Desktop
  ↓ app-server / 原生 Codex Harness
Codex Responses request
  ↓ HTTP 127.0.0.1，真实 Responses 合同
AiCli.GeminiAntigravityResponsesBridge
  ↓ stdin/stdout，结构化模型决策
Antigravity consumer backend
  ↓ Google 账号 consumer OAuth / AI Pro quota
Gemini 3.8 Flash High

工具执行方向：Gemini tool intent → Responses function_call → Codex Harness → tool output → 下一次 Responses request → Gemini
```

明确不是以下结构：

```text
Codex Desktop → Antigravity Harness → Antigravity 自己读文件/跑命令/调 MCP
```

也不以逆向 OAuth、抓取私有 Google endpoint、复用浏览器 cookie、导出 token 或购买 Gemini API Key 来达成目标。

### 22.2 2026-09-17 已验证事实

本机已安装并由 PCConfig 管理官方 `agy 1.2.5`，安装位置当前为 `E:\Program\AntigravityCLI\agy.exe`。`agy models` 当前真实列出 `gemini-3.8-flash-high / medium / low`；完成官方浏览器 consumer OAuth 后，`gemini-3.8-flash-high --effort high` 的最小调用真实返回 `SUCCESS`、有效 conversation id 与 input/output/thinking/total usage，证明当前账号、AI Pro entitlement 和模型通道可用。设计与运行时不得把本次一次性 OAuth code、账号标识或任何 token 写入仓库、日志、argv、测试快照或回执。

`agy --help` 和官方 Headless 合同当前提供 `--model`、`--effort low|medium|high`、`--agent`、`--input-format stream-json`、`--output-format stream-json`、`--json-schema`、`--sandbox`、`--disable-slash-commands` 和超时控制。`stream-json` 可保持一个进程并从 stdin 接收 `{"event":"user","message":{"content":"..."}}` NDJSON，每轮返回一个 `result`；usage/turn 等会话字段是累计量，逐轮统计必须做单调差分。`--json-schema` 的真机探针已经得到 `structured_output`，所以工具意图不需要靠自然语言正则解析。

普通 headless 默认 Agent 不能作为“裸模型”使用：真机 `init.tools` 仍暴露文件、Shell、Browser、Web、MCP、subagent、task 等大量工具，即使同时使用 `--sandbox --disable-slash-commands --mode plan`。因此生产门禁必须依赖专用 custom agent 的零工具运行态，而不能把 sandbox 或 prompt 约束误当成工具剥离。

Antigravity 当前官方 custom-agent 合同允许工作区 `.agents/agents/<name>/agent.md` 或全局 `~/.gemini/config/agents/<name>/agent.md`，`tools` 是显式工具列表、默认空数组，`subagent` 可以关闭，`commandExecutionPolicy` 可以设 `off`。当前 CLI changelog 还提供 `excludeDefaultComponents: true` 用于剥离默认 prompt sections / built-in tools。官方 Hooks 的 `PreToolUse` 支持 `matcher: "*"` 和 `decision: "deny"`，可以作为零工具 Agent 之外的独立硬拒绝层。由于既往版本存在默认组件残留的上游问题，最终判断只认本机 `init.tools` 与强制工具负测，不认配置字面值。

本机 Antigravity 自带的公开 Python SDK 参考确认 `response.thoughts` / `response.tool_calls`，上游源码确认 `CapabilitiesConfig(enabled_tools=[], enable_subagents=false)` 会把禁用工具从模型上下文移除。这条接口在技术上更适合“模型后端”，但当前公开认证文档只明确 API Key/Vertex/ADC，没有证明 consumer OAuth + Google AI Pro subscription entitlement。因此 SDK 只能做 P0 认证探针，不能作为既定生产路线。

当前 Codex 的真实 loopback capture 显示第三方 Responses 首请求包含：`model`、`instructions`、`input`、`tools`、`tool_choice`、`parallel_tool_calls`、`reasoning`、`store=false`、`stream=true`、`include`、`prompt_cache_key` 和 `client_metadata`。当前工具集合同时存在普通 `function`（例如 `exec_command`、`write_stdin`、`request_user_input`、`view_image`）、`namespace`（`multi_agent_v1`）和 `web_search`；`reasoning` 当前形态为 effort + summary，请求还要求 `reasoning.encrypted_content`。适配器必须覆盖这些真实形态，不能只实现“prompt → text”。

现有 DesktopBridge 已有正确职责边界：官方 Codex 引擎继续拥有 authentication/history/tools/execution，Bridge 只做受管模型目录、Provider/thread 路由和必要的 reasoning 展示归一化。GLM/DeepSeek 已有 raw reasoning → summary 通用路径，DeepSeek 另有经真人验收的 keep-alive 修正。Gemini 施工必须在此基础上增加 Provider，而不是把 DesktopBridge 改造成第二个 Agent。

### 22.3 组件与责任边界

新增独立组件建议命名 `AiCli.GeminiAntigravityResponsesBridge`。它是 AICLI-owned、按需启动的本地 Responses adapter，只监听 `127.0.0.1`，端口必须走现有 AICLI/PCConfig 端口合同；禁止绑定公网、修改防火墙、抢占未知 listener 或用管理员权限“解决端口”。DesktopBridge 继续负责模型目录和 thread provider 绑定，不直接承担 HTTP 协议翻译。

Responses Bridge 只做六件事：验证 Codex `/v1/responses` 请求；规范化 instructions/input/tool schema；驱动一个零工具 Antigravity model session；把结构化 final/tool intent 转成标准 Responses SSE；把公开 thought/visible summary 转成合法 reasoning summary；管理请求取消、超时和该 backend session 的生命周期。它不得执行任何 Codex tool，不得自行访问用户 workspace，不得保存通用聊天历史。

Antigravity backend 只能看到为当前模型决策所必需的 Codex 输入、工具“定义”和工具“结果”。所谓 Codex tool 在 Antigravity 侧只是数据结构，不注册为 Antigravity MCP/tool，不授予文件、命令、浏览器、网络或子代理能力。

Codex thread/history 是唯一恢复事实源。Antigravity `conversation_id` 只允许作为当前 bridge process 内部的易失运行标识，不能冒充 Codex thread id、不能进入用户回执、不能成为恢复权威。生产禁止 `--continue`；进程丢失后从 Codex 当前 Responses 输入重新建立 backend session，而不是从“最近一个 Antigravity 会话”猜恢复。`--conversation` 也不作为正常恢复合同。

### 22.4 Profile、模型目录与 effort 合同

首个入口：

```text
Profile ID:      codex-gemini-3-8-flash-antigravity
Visible model:   Gemini 3.8 Flash
Provider label:  Google Antigravity
Exact model:     gemini-3.8-flash-high
Transport:       managed-proxy
Codex-facing:    wire_api = responses
Fallback:        false / none
Auth to Google:  official Antigravity consumer OAuth only
```

Profile ID 带 `antigravity`，用于和未来可能出现的 Google 官方 Responses/API 入口区分；用户界面不需要把内部 transport 写进模型名。模型 identity 必须在启动前和 backend `init.model` / result 回读中同时验证，未知/消失/自动替换都失败关闭。Antigravity Headless 对未知 `--model` 会非零失败，该行为必须保留，不加 alias/fallback。

只公开真实的 `low/medium/high`。默认 `high`；Codex `low→low`、`medium→medium`、`high→high`。`max/xhigh` 在 Google 当前接口没有同名含义，第一版目录不得宣称支持。若 Desktop 只接受既有统一档位集合，则适配层必须在模型目录层限制选择而不是悄悄把 max 映成 high；任何兼容映射都需要用户可见且写入最终合同后再实施。

Gemini 3.8 Flash High 的可靠 context window、最大输出、图片输入和 compact 边界必须从当期官方模型元数据或可复现真机证据确认。确认前不得照搬 GLM/Qwen 的 1M 或本地模型 256K。确认后继续遵守非 OpenAI Codex 模型在最大上下文 90% 自动压缩的项目统一合同。

### 22.5 Antigravity 零工具隔离合同

生产 backend 使用专用空 workspace，不把用户项目目录、Codex workspace 或 `--add-dir` 交给 Antigravity。workspace 只包含受管 custom agent、静态输出 schema 和 deny-all hook，不包含项目源码、凭据、用户文件或其他技能。

候选 Agent 形态：

```yaml
---
name: aicli-codex-model-bridge
description: Model-only backend for the AICLI Codex Responses adapter.
tools: []
mainAgent: true
subagent: false
model: inherit
commandExecutionPolicy: off
excludeDefaultComponents: true
---
You are the model backend for a Codex Responses adapter. Never perform external actions.
Return only the requested structured public summary, final answer, or virtual Codex tool intent.
```

实际字段仍以当期 `agy` 解析器为准。启动固定包含 `--agent aicli-codex-model-bridge --model gemini-3.8-flash-high --disable-slash-commands`，并可叠加 `--sandbox` 作为 defense-in-depth；永不使用 `--dangerously-skip-permissions`。

同一 workspace 配置 `PreToolUse matcher="*" → decision="deny"`。Readiness 必须读取第一条 `init`：`model` 必须 exact，agent 必须 exact，`permission_mode` 不得是 always-proceed，`tools` 必须为空或仅包含经过设计明确证明无副作用且协议必需的 closed set。`run_command`、file read/write、browser、web/search、MCP、subagent、schedule、task/inbox 等任一出现都阻断 Provider，而不是“相信 prompt 不会调用”。另做恶意 prompt 负测，要求模型主动尝试命令/文件操作时零副作用、零 tool success。

bridge 启动 Antigravity 子进程时必须 scrub Codex/OpenAI/其他 Provider 的敏感环境变量；Google consumer OAuth 由官方客户端自己的凭据机制访问，AICLI 不从 `.gemini`、Windows Credential Manager 或浏览器导出 token。用户任务、instructions、工具定义和工具输出只走 stdin，不进 argv；静态 `--json-schema` 使用不含用户内容的受管文件。

### 22.6 Codex Responses → Gemini 决策协议

Bridge 把每个 Codex request 视为权威输入。`instructions`、`input` message、先前 `function_call`、`function_call_output`、tool choice 和当前 tools 都规范化后通过 stdin 发送给 Gemini。若保持一个 `agy --input-format stream-json --output-format stream-json` warmed process，只允许“同一 Codex thread、同一 Provider、同一模型、同一 instructions/tool schema 指纹”的连续请求共享；当前规范输入必须以已经发送的规范序列为严格前缀。前缀不一致、thread/provider/model/tool schema/effort 改变、进程丢失或事件序列不可验证时，销毁易失 session 并从当前 Codex request 重建，绝不拼接或猜测。

结构化输出第一版使用稳定、扁平、易验证的 schema，避免依赖复杂 JSON Schema 条件分支。语义至少包括：

```json
{
  "kind": "final | tool_calls",
  "visible_summary": "给用户看的简洁进度/理由摘要",
  "final_text": "仅 final 使用，否则为空字符串",
  "tool_calls": [
    {
      "tool_index": 0,
      "arguments_json": "{...}"
    }
  ]
}
```

工具名称不让模型自由发明。Bridge 把当前 request 的可调用工具按稳定索引呈现给 Gemini，返回后用 `tool_index` 反查原始 tool；再对 arguments 作 JSON 解析、schema 校验和大小/数量限制。`call_id` 由 Bridge 生成，不信任模型自由字符串。`parallel_tool_calls=false` 时最多一个调用；为 true 时仍设合理上限。任何未知索引、非法参数、重复 call、schema 不匹配或结构化结果缺字段都失败关闭；不得降级为从自然语言/Markdown/代码块正则提取工具调用。

普通 function intent 转成标准 Responses `function_call` output item，由 Codex Harness 真正执行；下一次 Codex request 带回该 `function_call` 与对应 `function_call_output` 后再交给 Gemini 继续。`request_user_input`、`exec_command`、`write_stdin`、`view_image` 等只要是当前 request 明确提供的 function tool，都遵守同一闭环。

`namespace`（当前真实存在 `multi_agent_v1`）必须保留 namespace + nested tool identity，不扁平碰撞；最终执行仍由 Codex Harness。Gemini 自己的 subagent 永久关闭。

`web_search` 不能偷偷改成 Antigravity `search_web`。AICLI 的 Codex harness 已有自己的 `public_web_search` 动态工具合同；下一局必须先捕获“当前 Codex 对 provider `web_search` 的真实执行/回传语义”，决定是投影为 Codex dynamic tool 还是其他受管 item。在该闭环实证前，Gemini 不得调用 web_search，也不得让 Antigravity代替搜索。

CLI stream-json 当前官方输入只承诺文本 content；所以第一版若选 CLI backend，`input_image` 等非文本输入必须显式标不支持并失败关闭，不能把图片路径暴露给 Antigravity 文件工具。只有找到无需文件工具、可验证的官方媒体传输接口后再开放多模态。

### 22.7 Responses SSE 与流式策略

Codex-facing adapter 必须产生当前 Codex 能接受的标准 Responses SSE 生命周期，而不是让 DesktopBridge 猜自由文本。第一版优先协议正确性：等待 Antigravity 每轮 `result.structured_output` 后再确定 final/tool call；中途 `agent_response text_delta` 不能在未证明与 structured result 一致时直接当最终正文释放。

若 backend 有明确公开 thought stream，可实时生成 reasoning started/summaryPartAdded/summaryTextDelta/completed；否则 `visible_summary` 在结构化结果确认后生成一个公开 reasoning summary item，再发 tool call 或 final。该 summary 是模型显式写给用户看的 rationale/progress，不宣称是 hidden chain-of-thought。

如果后续真机证明 custom agent 的文本 delta 和最终结构化字段存在可验证一一对应关系，可以在不改变语义的前提下增加流式摘要/正文优化。性能优化不得先于协议和取消语义。

### 22.8 Reasoning、进度引导与 Desktop 展示

Gemini 目录必须调用现有 `scripts/CodexUserCommunicationPolicy.ps1`，继承当前非 OpenAI Codex 模型的统一用户沟通策略：默认简体中文；需要调查/工具/多步任务时首次工具调用前主动发可见进度；重要发现、实质阶段进展、方向变化或影响结果的阻碍继续说明；无新信息不机械重复；最终答复补足背景、依据、已验证与未知。

如果 backend 正式暴露公开 reasoning/thought 文本，Gemini Provider 登记到通用 raw-reasoning normalization，复用 GLM 的 content→summary 语义并覆盖 `thread/read`、`thread/resume`、`thread/turns/list`、`thread/items/list`。如果只暴露 `thinking_tokens`，只使用 `visible_summary`，不能根据 token 数、工具动作或助手私有状态拼造“思考过程”。

Gemini 默认不进入 `DeepSeekTurnState`。先把真实 Gemini event trace 输入 `Invoke-RendererReplay.cjs` 对当前 Codex Desktop 的真实 projector/grouping 做回放；只有确实复现“正文尾部导致 reasoning 活动区提前关闭”才设计 Gemini-specific keepalive，而且仍必须是空结构项、不得生成假思考文本。GLM、DeepSeek、Qwen 和官方 Provider 的现有事件行为必须在回归中保持不变。

### 22.9 会话、持久化、恢复与隐私

Codex thread 是唯一长期会话。Antigravity warmed session只是一层易失推理缓存。不能把 Antigravity conversation id 写成 AICLI 的第二历史库，也不能在 Codex resume 时用 Antigravity 历史覆盖/补齐 Codex。

Antigravity CLI 当前会在 `~/.gemini/antigravity-cli/brain/<conversationId>` 等目录产生 transcript/artifact 类状态。下一局 P0 必须确定可关闭、隔离或在 backend session 结束后安全定向清理的方法。若必须保留，AICLI Provider 不得正式开放，直到能证明任务正文不会进入 AICLI/Git/备份/Doctor/日志的持久面。现有 `gemini-memory` 已过滤 conversation/history/log/cache，但“没备份”不等于“本机可无限留任务正文”。清理只能按本次 backend 返回的 exact conversation id 定向处理，绝不扫描/删除用户普通 Antigravity 会话。

每个请求取消、Codex 客户端断开、turn cancel 或 deadline 都必须取消/终止对应 Antigravity turn；不得在 Codex 已停止后后台继续消耗额度。若必须杀掉 per-thread warmed process，该 session 直接废弃，下一请求从 Codex 权威输入重建。

usage 使用 Antigravity result 的真实 input/output/thinking/cache/total；在一个 stream-json process 中它们是累计计数，每轮回执用单调快照差分。计数器回退、缺字段或跨 session 拼接不得伪装为精确 usage。

### 22.10 Python SDK 优化探针

下一局可在隔离 venv 安装官方 PyPI `google-antigravity`，但测试环境不得设置 `GEMINI_API_KEY`、Vertex API key 或 ADC，也不得读取/复制现有 OAuth token。唯一问题是：“SDK 在当前 Windows 用户下能否由官方方式复用同一 Antigravity consumer OAuth / Google AI Pro entitlement？”

若答案为是，再验证：`CapabilitiesConfig(enabled_tools=[], enable_subagents=false)` 的真实 model context 无 builtin/MCP tool；exact `gemini-3.8-flash-high` 可选；thought stream、structured output、取消、usage 和 entitlement 与 CLI 一致。全部通过后 SDK 可作为更干净的 backend driver，Codex-facing Responses Bridge 与上层设计不变。

若答案为否或要求 API Key/Vertex 计费，立即停止这条路线并清理 probe venv/临时文件；不能为了接口漂亮牺牲用户“复用 Google AI Pro”的核心目标。

## 25. 后台 OpenAI 同会话协作

### 25.1 用户目标与边界

2026-09-18 用户要求：第三方父任务能够在 Luna 完成后继续追问同一个会话，运行中双方可以发送补充信息、进度和问题；不改成独立顶层任务，也不要求用户充当消息搬运者。本项完善后台协作，不承诺原生子代理卡片、可点击的子代理面板或伪造原生父子身份。

实现仍使用同一个官方 Codex app-server。模型推理、工具执行、上下文、自动压缩与会话历史全部由官方引擎负责；AICLI 只适配生命周期和消息投递，不创建第二个 Agent 引擎、不直连 OpenAI HTTP、不复制聊天正文到自建账本。OpenAI 入口继续固定官方 Provider，模型与思考等级由现行授权及宿主目录决定；没有扩展第三方之间的横向路由。

### 25.2 协作工具与真实语义

- 父任务使用 `openai_child`。首次传入既有 `agent_type/model/reasoning_effort/task_name/message` 创建后台会话；完成后加上返回的 `thread_id`，保持该子会话的模型、思考等级和任务名，继续同一会话。运行中发送新消息同样使用这一入口，不创建替身。
- `openai_child` 默认最多等待一秒，可用 `wait_ms` 调整至零到三十秒。返回 `running` 只证明受理，不证明完成；最终答案和重要事件通过官方 `thread/inject_items` 进入父任务的机器上下文，不生成无对应调用 ID 的工具输出。父任务忙时由官方引擎排队；空闲时使用空输入加 untrusted additionalContext 唤醒。消息带来源标记且没有真人输入结构标签，不是新的授权。
- 子任务使用 `openai_parent` 向其真实绑定的父任务发消息。`request_reply=false` 汇报进度后继续；`request_reply=true` 等待父任务回复。父任务在 `openai_child` 中传同一 `thread_id` 和问题的 `reply_to`，回复真正写回子任务工具后才确认投递。
- 父任务使用 `openai_child_control` 的 `list/status/wait/stop` 发现自己的子会话、查询状态、等待变化或中断当前回合。停止保留会话；后续授权内追问继续同一会话。父任务最终交付前应结清或停止其未完成分工，不把一次确认答复说成无限期待命。

首次上下文由父任务提供；后续上下文来自同一官方会话历史，不把父任务完整历史自动复制给子任务。完成一轮不等于关闭会话；不同父任务不能借会话 ID 操作对方的子会话。
